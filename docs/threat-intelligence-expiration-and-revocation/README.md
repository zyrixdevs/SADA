# Threat Intelligence Expiration and Revocation

**Catalogue module 48 of 49. Status: proposed specification only; not implemented or deployed.**

## Purpose

Provide one lifecycle for intelligence freshness, correction, withdrawal and propagation across consumers.

## What it does

Evaluate validity on read and dispatch; mark stale/expired; accept authorized correction; append revision; cancel pending outbox deliveries; emit correction event; retain historical lineage under retention policy.

## What it must never do

- It must not execute Discord moderation or configuration changes. Zyrix Bot remains the only Discord action boundary and rechecks local consent, permissions and role hierarchy.
- It must not treat a score, anomaly or single report as proof or punishment authority.
- It must not bypass guild opt-in, shared case/review, evidence, identity or audit contracts.

## Signals and workflow

**Inputs:** Indicator/revision refs; source validity; evidence status; expiry policy; correction/reversal event; downstream pending deliveries.

```mermaid
flowchart LR
 A[Authorized source event or advisory] --> B[Validate scope, version and consent]
 B --> C[Normalize and preserve provenance]
 C --> D[Module-owned analysis: Threat Intelligence Expiration and Revocation]
 D --> E[Versioned explainable finding]
 E --> F[Shared incident, case and review services]
 F --> G[Scoped advisory or Zyrix local decision]
 C --> H[Canonical audit and correction path]
```

Lifecycle state is active, stale, expired, disputed, revoked or superseded; no state is overwritten without revision. Expiry differs from retraction; consumers receive idempotent revision notifications.

## Ownership and integration

This module owns only domain-specific observations, snapshots, assessments and indicator references. It reuses canonical installation/consent, event inbox, incident/evidence, case/review, delivery/outbox and audit records. It does not create separate authentication, case management, evidence vault, reviewer quorum or audit systems.

Dependencies: [Evidence Vault](../evidence-vault/README.md), [Threat Intelligence Network](../threat-intelligence-network/README.md), [Security Advisory Network](../security-advisory-network/README.md), [Global Ban System](../global-ban-system/README.md), External Threat Feeds..

## Security, privacy and limitations

Only authorized source can retract; corrections propagate promptly; audit reads and transitions; prevent malicious mass revocation through scoped approvals. Expiration does not prove an indicator was false; historical decisions must retain the version actually seen and later correction linkage.

Cross-guild sharing requires explicit purpose and permission. Missing, stale or inaccessible data is represented as unknown/partial. Corrections and revocations are versioned and propagate to pending deliveries.

## API and event contract

**Method:** `POST`. Proposed internal endpoint: `POST /v1/intelligence/{id}/revisions`. It uses the shared `/v1` authentication and authorization model, guild scope from authenticated grants, request ID, schema version, idempotency key, bounded JSON payload, and shared error shape. The endpoint accepts observations or recommendations only; it does not execute Discord actions. A durable inbox receipt is returned only after commit. Duplicate key + same canonical body returns the original receipt; changed body returns `409`. Retry only transient `retryable=true` errors.

Example request:

```json
{
  "schema_version": "1.0",
  "event_id": "018f0000-0000-7000-8000-000000000001",
  "source_guild_id": "123456789012345678",
  "occurred_at": "2026-11-16T10:00:00Z",
  "consent_version": "guild-consent-7",
  "correlation_id": "018f0000-0000-7000-8000-000000000003",
  "payload": { "observation_ref": "opaque-reference", "type": "module-specific" }
}
```

Example accepted response:

```json
{"event_id":"018f0000-0000-7000-8000-000000000001","receipt_id":"018f0000-0000-7000-8000-000000000004","status":"accepted","duplicate":false}
```
