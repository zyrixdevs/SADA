# OAuth and Third-Party App Security

**Catalogue module 21 of 49. Status: proposed specification only; not implemented or deployed.**

## Purpose

Detect risky OAuth grants and third-party integration changes using authorized configuration metadata.

## What it does

Capture integration lifecycle event; validate source guild scope; compare requested/current permissions against policy; emit explainable risk delta; require authorized reviewer/administrator before advisory or remediation recommendation.

## What it must never do

- It must not execute Discord moderation or configuration changes. Zyrix Bot remains the only Discord action boundary and rechecks local consent, permissions and role hierarchy.
- It must not treat a score, anomaly or single report as proof or punishment authority.
- It must not bypass guild opt-in, shared case/review, evidence, identity or audit contracts.

## Signals and workflow

**Inputs:** Integration ID/type; application ID; permission bitset; install/update/remove audit events; authorized guild configuration snapshot; actor attribution confidence.

```mermaid
flowchart LR
 A[Authorized source event or advisory] --> B[Validate scope, version and consent]
 B --> C[Normalize and preserve provenance]
 C --> D[Module-owned analysis: OAuth and Third-Party App Security]
 D --> E[Versioned explainable finding]
 E --> F[Shared incident, case and review services]
 F --> G[Scoped advisory or Zyrix local decision]
 C --> H[Canonical audit and correction path]
```

Compare permission sets and integration owner/version snapshots. Flag Administrator or unexpected scope additions as review facts, not compromise conclusions. Version policy and include exact added/removed permissions.

## Ownership and integration

This module owns only domain-specific observations, snapshots, assessments and indicator references. It reuses canonical installation/consent, event inbox, incident/evidence, case/review, delivery/outbox and audit records. It does not create separate authentication, case management, evidence vault, reviewer quorum or audit systems.

Dependencies: [Security Health Monitor](../security-health-monitor/README.md), [Bot Permission Drift Detection](../bot-permission-drift-detection/README.md), [Privilege Escalation Path Analyzer](../privilege-escalation-path-analyzer/README.md), Configuration Drift Detection..

## Security, privacy and limitations

Never store OAuth access/refresh tokens; encrypt sensitive integration owner references; guild admin can access only their own snapshots. Discord may not expose OAuth token scope or publisher history to the bot; unavailable fields remain unknown, never inferred.

Cross-guild sharing requires explicit purpose and permission. Missing, stale or inaccessible data is represented as unknown/partial. Corrections and revocations are versioned and propagate to pending deliveries.

## API and event contract

**Method:** `POST`. Proposed internal endpoint: `POST /v1/integrations/oauth-observations`. It uses the shared `/v1` authentication and authorization model, guild scope from authenticated grants, request ID, schema version, idempotency key, bounded JSON payload, and shared error shape. The endpoint accepts observations or recommendations only; it does not execute Discord actions. A durable inbox receipt is returned only after commit. Duplicate key + same canonical body returns the original receipt; changed body returns `409`. Retry only transient `retryable=true` errors.

Example request:

```json
{
  "schema_version": "1.0",
  "event_id": "018f0000-0000-7000-8000-000000000001",
  "source_guild_id": "123456789012345678",
  "occurred_at": "2026-11-16T10:00:00Z",
  "consent_version": "guild-consent-7",
  "correlation_id": "018f0000-0000-7000-8000-000000000003",
  "payload": { "observation_ref": "opaque-reference", "type": "module-specific" }
}
```

Example accepted response:

```json
{"event_id":"018f0000-0000-7000-8000-000000000001","receipt_id":"018f0000-0000-7000-8000-000000000004","status":"accepted","duplicate":false}
```
