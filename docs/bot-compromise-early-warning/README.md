# Bot Compromise Early Warning

**Catalogue module 23 of 49. Status: proposed specification only; not implemented or deployed.**

## Purpose

Surface suspicious bot behavior and external compromise warnings early for human investigation.

## What it does

Ingest events and known compromise advisory; compare behavior against service-specific recent baseline; identify explainable anomalies; link incident/timeline; recommend owner verification and token rotation through the bot operator’s own controls.

## What it must never do

- It must not execute Discord moderation or configuration changes. Zyrix Bot remains the only Discord action boundary and rechecks local consent, permissions and role hierarchy.
- It must not treat a score, anomaly or single report as proof or punishment authority.
- It must not bypass guild opt-in, shared case/review, evidence, identity or audit contracts.

## Signals and workflow

**Inputs:** Bot-originated moderation/configuration event types; event rates; failed/unknown attribution; reviewed external advisories; bot permission baseline diffs.

```mermaid
flowchart LR
 A[Authorized source event or advisory] --> B[Validate scope, version and consent]
 B --> C[Normalize and preserve provenance]
 C --> D[Module-owned analysis: Bot Compromise Early Warning]
 D --> E[Versioned explainable finding]
 E --> F[Shared incident, case and review services]
 F --> G[Scoped advisory or Zyrix local decision]
 C --> H[Canonical audit and correction path]
```

Use feature flags and per-bot history; separate observed action from inferred compromise. Destructive action class, velocity deviation and permission change remain separate factors; no universal threshold or automatic shutdown.

## Ownership and integration

This module owns only domain-specific observations, snapshots, assessments and indicator references. It reuses canonical installation/consent, event inbox, incident/evidence, case/review, delivery/outbox and audit records. It does not create separate authentication, case management, evidence vault, reviewer quorum or audit systems.

Dependencies: [Suspicious Admin Activity](../suspicious-admin-activity/README.md), [Destructive Action Circuit Breaker](../destructive-action-circuit-breaker/README.md), [Bot Security Intelligence](../bot-security-intelligence/README.md), Emergency Response Playbooks..

## Security, privacy and limitations

Do not request/store tokens; token rotation is a recommendation to authorized operator, never automated; restrict alert visibility. A legitimate release or staff operation may resemble compromise. Hosting provider/IP signals are not assumed available and are not shared without consent.

Cross-guild sharing requires explicit purpose and permission. Missing, stale or inaccessible data is represented as unknown/partial. Corrections and revocations are versioned and propagate to pending deliveries.

## API and event contract

**Method:** `POST`. Proposed internal endpoint: `POST /v1/bot-compromise/observations`. It uses the shared `/v1` authentication and authorization model, guild scope from authenticated grants, request ID, schema version, idempotency key, bounded JSON payload, and shared error shape. The endpoint accepts observations or recommendations only; it does not execute Discord actions. A durable inbox receipt is returned only after commit. Duplicate key + same canonical body returns the original receipt; changed body returns `409`. Retry only transient `retryable=true` errors.

Example request:

```json
{
  "schema_version": "1.0",
  "event_id": "018f0000-0000-7000-8000-000000000001",
  "source_guild_id": "123456789012345678",
  "occurred_at": "2026-11-16T10:00:00Z",
  "consent_version": "guild-consent-7",
  "correlation_id": "018f0000-0000-7000-8000-000000000003",
  "payload": { "observation_ref": "opaque-reference", "type": "module-specific" }
}
```

Example accepted response:

```json
{"event_id":"018f0000-0000-7000-8000-000000000001","receipt_id":"018f0000-0000-7000-8000-000000000004","status":"accepted","duplicate":false}
```
