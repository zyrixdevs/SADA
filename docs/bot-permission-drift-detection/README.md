# Bot Permission Drift Detection

**Catalogue module 22 of 49. Status: proposed specification only; not implemented or deployed.**

## Purpose

Compare observed bot permissions with an explicitly approved least-privilege baseline.

## What it does

Record baseline approval and its source; ingest permission changes; compute set difference; classify new high-impact bits and scope; notify local admins; generate a reviewable least-privilege recommendation.

## What it must never do

- It must not execute Discord moderation or configuration changes. Zyrix Bot remains the only Discord action boundary and rechecks local consent, permissions and role hierarchy.
- It must not treat a score, anomaly or single report as proof or punishment authority.
- It must not bypass guild opt-in, shared case/review, evidence, identity or audit contracts.

## Signals and workflow

**Inputs:** Bot role ID; role permission bitset; channel overwrites; role hierarchy; approved baseline revision; role update audit event.

```mermaid
flowchart LR
 A[Authorized source event or advisory] --> B[Validate scope, version and consent]
 B --> C[Normalize and preserve provenance]
 C --> D[Module-owned analysis: Bot Permission Drift Detection]
 D --> E[Versioned explainable finding]
 E --> F[Shared incident, case and review services]
 F --> G[Scoped advisory or Zyrix local decision]
 C --> H[Canonical audit and correction path]
```

Use canonical permission identifiers and baseline revision. Administrator is a critical finding; recommendations list exact permission bits and affected channels. Absence of complete channel data produces partial assessment.

## Ownership and integration

This module owns only domain-specific observations, snapshots, assessments and indicator references. It reuses canonical installation/consent, event inbox, incident/evidence, case/review, delivery/outbox and audit records. It does not create separate authentication, case management, evidence vault, reviewer quorum or audit systems.

Dependencies: [Security Health Monitor](../security-health-monitor/README.md), [OAuth and Third-Party App Security](../oauth-and-third-party-app-security/README.md), [Privilege Escalation Path Analyzer](../privilege-escalation-path-analyzer/README.md), Configuration Drift Detection..

## Security, privacy and limitations

Baseline changes require guild administrator confirmation and audit; never store bot token; display exact scope and data freshness. A baseline can be stale or intentionally changed; drift is not automatically malicious and must not trigger role modification.

Cross-guild sharing requires explicit purpose and permission. Missing, stale or inaccessible data is represented as unknown/partial. Corrections and revocations are versioned and propagate to pending deliveries.

## API and event contract

**Method:** `POST`. Proposed internal endpoint: `POST /v1/bot-permission/observations`. It uses the shared `/v1` authentication and authorization model, guild scope from authenticated grants, request ID, schema version, idempotency key, bounded JSON payload, and shared error shape. The endpoint accepts observations or recommendations only; it does not execute Discord actions. A durable inbox receipt is returned only after commit. Duplicate key + same canonical body returns the original receipt; changed body returns `409`. Retry only transient `retryable=true` errors.

Example request:
```json
{
  "schema_version": "1.0",
  "event_id": "018f0000-0000-7000-8000-000000000001",
  "source_guild_id": "123456789012345678",
  "occurred_at": "2026-11-16T10:00:00Z",
  "consent_version": "guild-consent-7",
  "correlation_id": "018f0000-0000-7000-8000-000000000003",
  "payload": { "observation_ref": "opaque-reference", "type": "module-specific" }
}
```

Example accepted response:
```json
{"event_id":"018f0000-0000-7000-8000-000000000001","receipt_id":"018f0000-0000-7000-8000-000000000004","status":"accepted","duplicate":false}
```
